# BRD Generator

## 何时使用

当输入同时包含当前需求描述、BRD 规范、历史 BRD 示例、已有 BRD 或项目代码摘要，并要求生成或完善当前 BRD 时使用本 Skill。

## 事实优先级

按以下顺序解决冲突：

1. 当前需求名称与描述；
2. 当前项目代码、配置和展示摘要所证明的现状；
3. 当前项目 BRD 规范；
4. 已有当前 BRD 中仍与前三项一致的内容；
5. 历史 BRD 中可复用的结构、术语和表达习惯。

历史 BRD 不是当前项目事实来源。不得把历史文档中的品牌、系统、接口、时间、指标、范围或结论直接复制到当前 BRD。代码只能证明当前实现现状，不能代替未明确给出的业务决策。

## 执行流程

1. 从历史 BRD 中提炼稳定的章节结构、需求粒度、术语、验收表达和风险表达；丢弃具体旧事实。
2. 从项目代码摘要中识别当前已有入口、能力、数据、接口和约束，并区分“已实现”“推断”“待确认”。
3. 以当前需求为最高约束生成完整 BRD 初稿；若已有当前 BRD，保留仍有效内容并做增量完善。
4. 对初稿执行内部质量审查：
   - 规范要求的章节是否齐全；
   - 目标、范围、功能需求和验收标准是否互相一致；
   - 每条功能需求是否具体、可测试、可追踪；
   - 是否把代码现状误写成业务要求，或把推断误写成事实；
   - 是否遗漏兼容性、权限、数据、异常、依赖、风险和待确认项；
   - 是否残留历史 BRD 的无关事实；
   - 是否存在空洞措辞、重复段落或无法验收的形容词。
5. 根据审查结果修订全文。最多执行 3 轮“审查 → 修订”；当上述检查均无阻断缺口时提前停止。
6. 输出最终 BRD，不输出草稿、评分、审查过程或解释。

## 输出契约

- 只输出完整 Markdown BRD，首行必须是一级标题。
- 至少覆盖：背景与目标、用户与场景、范围、现状与增量、功能需求、非功能需求、依赖与约束、风险与待确认项、成功标准/验收要点。
- 功能需求使用稳定编号；验收标准应能被测试或人工明确判断。
- 未被输入证明的内容明确标记为“假设”或“待确认”，不得编造数据。
- 不使用 Markdown 代码围栏包裹全文，不输出开场白或结束语。

## 失败处理

- 当前需求描述为空或相互矛盾时，仍输出可确认的 BRD 骨架，并把阻断点集中列入“待确认项”。
- 历史 BRD 不可用时，依据当前需求、代码摘要和规范继续，不得声称已经参考历史材料。
- 代码摘要被截断或不足时，只陈述可证明的现状，并明确剩余验证项。

## 最终验证

返回前再次确认：首行为 `# `；章节完整；需求可验收；历史事实未串入；所有推断均有显式标记；输出中没有审查过程。
