解决什么？

手工分析，重复劳动，响应慢

  • 01
    手工分析 — Adobe 公告、CVE、补丁分散各处，每次都要人工拼装理解，成本高、易漏点
  • 02
    项目多 — 我们有很多 magento 项目，每个项目要逐一排查，工作量大
  • 03
    重复劳动 — 多个团队各自为战，都要排查同一公告，效率低
  • 04
    响应慢 — 从出公告到知道谁还没修，链路长、缺少追溯

价值

风险项级跟踪 · 双层证据 · 引入 AI 分析

  • 01
    按 RiskItem 跟踪 — 不以整份公告糊成一团，每条风险可独立入库与扫描

    版本 + 内容指纹 — 升级与补丁内容均可核验，结论带 evidence
  • 03
    引入 AI 分析 — 中文叙述、结构化辅助、指纹草稿，加速读懂与入库

扫描核心逻辑

怎么判断这个项目有没有漏洞

01

两道检查，规则匹配（无 AI 参与）

看版本先看项目装的 Magento / 包版本，有没有达到公告要求的安全版本。升上去了，一般就认定已修好。
看代码若没升级、只打了补丁：对比补丁前后的关键代码片段——还是旧代码 → 没修好；已是新代码 → 补丁打上了。多处改动要处处都对上才算。
02

结论怎么出

无关这个版本根本不在公告影响范围 → 标成「不适用」
已升级版本已经够新 → 「已修复」
只打补丁版本还旧，但关键代码已变成补丁后的样子 → 「已修复」（靠补丁）
仍有风险版本还在影响范围，且代码仍是补丁前的样子 → 「未修复」
其他文件找不到、对不上、又没有可用指纹 → 「未修复」。
03

最后留下什么

详细记录每条结论都写清：修没修好、靠升级还是补丁，以及版本比对和代码检查的证据，方便事后核对。

AI 怎么分析

AI 帮忙读懂，规则负责下结论

AI 可以帮

  • 把官方公告 + NVD（及补丁信息）合在一起读懂
  • 写成人能看懂的中文：风险大不大、影响什么业务、怎么修
  • 从补丁里草稿出「改前 / 改后」代码对照，方便后面扫

AI 不能定

  • 哪个项目有没有修好——只看版本号和代码是否对上
  • 扫描结论、证据怎么记——全部走规则，可复查
  • 企微要不要再推——按状态去重，不靠模型临场发挥

一句话：AI 加快「读懂公告」；「这项目修了没」永远由规则说了算

怎么用

配置一次，定时跑通闭环

01

准备配置

做什么复制 settings.yaml、projects.yaml、.env；在项目列表里填 git 分支与负责人，密钥放环境变量勿写进仓库。
02

入库情报

命令msw ingest — 采集 Adobe 公告，拆成 RiskItem；可拉 NVD、补丁指纹，并可选 LLM 中文分析。
03

扫描项目

命令msw scan — 按配置拉分支（或 --local-workspace）；可加 --project 指定项目、--notify 边扫边通知。
04

查看结果与定时

日常msw status 看汇总；msw serve 开内网看板；需要时 msw notify。cron：先 ingest，再 scan --notify。

接下来做什么

覆盖更多现场，服务更多技术栈

01

没有 Git 仓库权限时怎么扫

问题部分项目无仓库读权限，或 vendor 不在 Git 里，当前「拉分支再扫」走不通。
做法支持本地/挂载目录直接扫描；或定期投递产物包（含 composer.lock 与关键代码）；权限更紧时只交版本清单做版本层判定；有权限的机器可跑轻量采集 Agent回传结果。
02

自动化渗透测试

问题渗透验证成本高、难常态化，难以覆盖多项目与多漏洞场景。
做法在测试环境上对未修复项做受控、可重复的自动验证（不碰线上）；结果回写看板并与通知联动。
03

其他框架、其他语言怎么支持

问题情报源、依赖锁文件、版本语义与补丁路径都绑在 Magento/PHP 上，无法直接套到 Node、Java 等栈。
做法把链路拆成可插拔的三块：Advisory（公告从哪来、怎么拆 RiskItem）、Inventory（npm / pip / maven 等怎么读版本）、Matcher（版本规则 + 指纹约定）。核心仍是 Bulletin → RiskItem → Finding，换适配器即可扩展。
